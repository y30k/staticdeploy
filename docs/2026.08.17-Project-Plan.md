# StaticDeploy Modernization Project Plan

## 1. Purpose and constraints

Modernize StaticDeploy into a secure, maintainable internal platform for publishing static browser applications.

This plan is intentionally organized by **dependencies, deliverables, and acceptance evidence**, not dates or staffing assumptions. Work should proceed in the smallest vertical slices that preserve a usable rollback point.

### Fixed constraints

- GitHub Actions is the **only CI/CD orchestration system**.
- CircleCI must be removed completely after equivalent work is migrated or explicitly retired.
- ArgoCD, Jenkins, GitLab CI, Buildkite, and other CI/CD controllers are out of scope and must not be introduced.
- GitHub Actions builds, tests, scans, signs, publishes, deploys, verifies, promotes, and rolls back releases.
- OCI images and OCI-packaged Helm charts are published only to GitHub Container Registry (`ghcr.io`).
- Any package that must be distributed outside the monorepo is published only to GitHub Packages; no package is published to public npm.
- The application uses PostgreSQL and S3-compatible object storage without prescribing a cloud provider or managed service.
- The supported deployment profiles are Kubernetes through Helm and a single Docker host through Docker Compose; Docker Compose is also the default local validation path.
- Cloud-resource authentication is configurable. Workload identity, instance/container identity, and explicitly supplied credentials are supported options; no provider-specific mechanism such as IRSA is required.
- Uploaded applications remain static-only and do not create per-application infrastructure resources.
- Uploaded content and the trusted management interface use isolated browser origins.
- This document is the planning source of truth. The project board at <https://github.com/orgs/y30k/projects/2/views/1> tracks execution after this plan is approved; this refinement does not add or modify board items or issues.

## 2. Desired product outcome

A nontechnical user can:

1. Find or create an application.
2. Upload one or more files directly, or upload a ZIP archive.
3. Select any uploaded HTML document as the default document; it does not need to be named `index.html`.
4. See validation and security findings.
5. Preview the upload on an isolated origin.
6. Publish or unpublish a timestamp-labeled version.
7. Download the preserved source files or source package.
8. Upload a later version.
9. Restore any retained version without rebuilding or copying its content.
10. See who performed each release operation and when it was published in the viewer's local time.

The platform remains one operated product. Publishing hundreds of applications must not create hundreds of Deployments, Services, Ingresses, containers, or upgrade lifecycles.

### 3.2 Explicit non-goals

- Arbitrary user containers or server-side application code
- Per-application databases, secrets, containers, or orchestration resources
- Serverless functions or stateful workflows
- Browser-based code editing
- Building source frameworks such as React or Next.js
- Replacing Git-based engineering delivery
- Connected applications that require authenticated backend APIs
- Public applications, custom domains, or external sharing
- A general-purpose application platform
- A broad visual redesign unrelated to the publishing workflow
- A new implementation language or wholesale rewrite

Runtime configuration injection may remain temporarily for verified compatibility needs, but it is disabled by default and must never deliver secrets to browsers.

## 4. Verified repository baseline

The current repository contains one executable CI/CD system: `.circleci/config.yml`. No GitHub Actions workflows or other checked-in CI/CD definitions exist.

CircleCI currently performs four jobs that must be migrated or retired deliberately:

| Current job | Current behavior | Modernization disposition |
| --- | --- | --- |
| `qa` | Node 14 build, lint, tests, PostgreSQL/MinIO integration coverage, Codecov upload | Recreate as GitHub Actions checks, then retire CircleCI job. Decide whether external Codecov remains necessary; GitHub Actions artifacts and summaries are the default. |
| `publish-website` | Builds and publishes the website for every branch and tag | Retire by default. If the website remains required, deploy it through a restricted GitHub Actions workflow rather than preserving branch-wide publication. |
| `docker-build-push` | Builds service and CLI images and pushes every branch/tag to Docker Hub | Replace with GitHub Actions Buildx workflows that publish approved releases only to `ghcr.io`. Retire Docker Hub publication. |
| `npm-publish` | Publishes public packages for `v*` tags | Retire public npm publication. Keep workspace packages private unless an approved external consumer requires a package; publish any such package only to GitHub Packages. |

Other verified legacy coupling that the migration must remove includes:

- CircleCI badges and release instructions
- `.circleci/config.yml` and its formatting exemption
- `CIRCLE_TAG`, `CIRCLE_BRANCH`, and `CIRCLE_SHA1` usage in website deployment configuration
- Docker Hub image names and push/tag scripts
- public npm `publishConfig` metadata and tag-triggered Lerna publication; any retained package publication must target GitHub Packages
- `master`-specific release and website behavior where the modern branch is `main`
- CircleCI, Docker Hub, npm, legacy website-deployment, and superseded coverage credentials or integrations

The existing implementation is a Yarn/Lerna TypeScript monorepo using Node 14-era tooling. Both Dockerfiles use Node 14, non-frozen installs within the image, a single build/runtime stage, and root execution. The core domain boundaries remain useful, so modernization should preserve behavior through characterization tests rather than start with a rewrite.

## 5. Simplification decisions

These decisions minimize work and reduce parallel migration paths.

1. **Preserve the TypeScript monorepo.** Upgrade it in place; do not rewrite in another language.
2. **Deliver one vertical product path first.** The first complete path is create application → upload multiple files → select the default HTML document → validate → preview → publish → download → restore.
3. **Use PostgreSQL for release-job state.** Start with a database-backed job/lease table and a worker process; do not add Kafka, RabbitMQ, or another queue unless measured load proves it necessary.
4. **Keep only necessary runtime separation.** Use a trusted control plane, an untrusted content plane, and a release worker. They may come from one repository and release but use distinct service accounts and permissions.
5. **Retain the existing component library.** Upgrade React and Ant Design, replace unsupported build/test tooling, and avoid a design-system rewrite.
6. **Default to retiring compatibility surfaces.** Preserve API v1, the legacy CLI, package publication, and the CLI image only if the baseline inventory identifies an approved consumer and an explicit acceptance test. Any retained package publication uses GitHub Packages.
7. **Do not build a generic migration framework without data to migrate.** First inventory actual production apps, bundles, URLs, and integrations. If none exist, record a greenfield decision and retire the legacy service rather than implementing migration tooling.
8. **Keep deployment portable.** GitHub Actions validates and can deploy either the Helm or Docker Compose profile using target-appropriate authentication and configuration. No cloud provider, cluster product, credential mechanism, or separate CD controller is prescribed.
9. **Use the organization-approved supported Node LTS at implementation time.** Pin the selected version in repository and CI configuration; do not make the plan depend on a forecasted calendar release.
10. **Make observability an onboarding dependency, not an invented integration.** Use only Eyes-provisioned product/environment routes and credentials after the platform gate opens.

## 6. Target architecture

```text
Users
  |
  v
Trusted origin
Control plane: portal, API, OIDC session, metadata
  |                  \
  |                   \ direct or presigned upload
  v                    v
PostgreSQL          S3-compatible quarantine
  |                    |
  | job/lease          v
  +--------------> Release worker
                       | validate, scan, unpack, hash
                       v
                 Immutable object-store releases
                       |
                       v
Untrusted origins
Content plane: published assets and isolated previews
```

### 6.1 Runtime components

| Component | Responsibility | Minimum permissions |
| --- | --- | --- |
| Control plane | Portal, API, OIDC sessions, application/release metadata, upload-session creation | PostgreSQL; limited quarantine upload access |
| Release worker | Claim jobs, validate files/packages, scan content, create manifests, write immutable releases | PostgreSQL job state; quarantine read/delete; release-prefix write |
| Content plane | Serve published assets and previews | Read-only release-prefix access |

The content plane never receives management cookies, OIDC tokens, database credentials, quarantine access, or object-store write access. Each deployment profile supplies storage credentials through its selected provider chain, workload/host identity, or secret mechanism.

### 6.2 Storage model

```text
object-store://static-apps/
  quarantine/{upload-id}/
    files/{relative-path}       # direct multi-file upload
    original.zip               # ZIP upload
  releases/{application-id}/{release-id}/
    source/{relative-path}      # preserved direct-upload source files
    original.zip               # preserved ZIP, when supplied
    source-download.zip        # deterministic archive for direct uploads
    manifest.json              # paths, digests, MIME types, default document
    content/{relative-path}
  rejected/{upload-id}/scan-report.json
```

PostgreSQL stores application metadata, immutable release metadata, the selected default-document path, current-release pointers, publication timestamps/version labels, authorization bindings, job state, and audit events. A publish, unpublish, or restore operation changes only the application pointer and audit record in one transaction.

Object keys do not need to use the content digest. Immutability is enforced by write-once release prefixes, authorization policy, and digest verification.

### 6.3 Minimal release state machine

```text
PENDING_UPLOAD
  -> UPLOADED
  -> PROCESSING
  -> AWAITING_DEFAULT_DOCUMENT
  -> READY

PROCESSING -> READY            # default document was already selected

PENDING_UPLOAD | UPLOADED | PROCESSING | AWAITING_DEFAULT_DOCUMENT
  -> FAILED
```

Required behavior:

- Upload completion is explicit and idempotent.
- A worker claims a job with a lease, renews or releases it, and can safely retry after interruption.
- Duplicate completion calls and worker retries do not create duplicate releases.
- Retry count, timeout, and terminal failure reason are bounded and recorded.
- Failed or expired uploads are removed from quarantine according to policy.
- A direct upload declares one or more relative file paths; a ZIP is expanded before its candidate HTML documents are presented.
- The selected default document must be a safe relative path to an uploaded `.html` or `.htm` file, but its filename is unrestricted.
- Only releases with a selected default document can become `READY`, be previewed, or be published.

### 6.4 Version and publication timestamps

- Every release has an internal opaque ID that is never derived from a timestamp.
- The first successful publish transaction stores `published_at` as an authoritative UTC timestamp and assigns the user-facing version label `YYYY.MM.DD-HH.mm.ss`, for example `2026.08.17-13.31.22`.
- If two first publications for the same application occur in the same second, append the smallest deterministic suffix (`-2`, `-3`, and so on) while retaining the full UTC timestamp internally.
- A restore or later republish keeps the release's original version label and creates a new publication audit event with its own UTC timestamp.
- The API returns machine-readable UTC timestamps. The browser displays `Published at {localized timestamp}` using the user's locale and timezone, while also making the UTC value available.
- Draft/ready releases that have never been published remain labeled as drafts until their first successful publication.

### 6.5 Minimal API v2

```text
POST   /api/v2/applications
GET    /api/v2/applications
GET    /api/v2/applications/{id}
POST   /api/v2/applications/{id}/archive
GET    /api/v2/applications/{id}/bindings
PUT    /api/v2/applications/{id}/bindings
GET    /api/v2/audit-events?application_id=&actor=&action=&from=&to=

POST   /api/v2/applications/{id}/releases
POST   /api/v2/releases/{releaseId}/complete-upload
POST   /api/v2/releases/{releaseId}/default-document
GET    /api/v2/applications/{id}/releases
GET    /api/v2/releases/{releaseId}
GET    /api/v2/releases/{releaseId}/download
POST   /api/v2/releases/{releaseId}/publish
POST   /api/v2/applications/{id}/unpublish
POST   /api/v2/applications/{id}/restore
```

Binding updates replace the application's complete binding set transactionally and require an idempotency key. Audit queries are paginated and apply bounded, indexed filters. Release creation accepts either a declared direct-upload file list or one ZIP upload. Default-document selection validates against the processed manifest. Publish, unpublish, restore, upload completion, default-document selection, binding updates, and job processing require idempotency guarantees. Release archival is deferred; every retained release therefore remains eligible for restore.

### Milestone 5 — ZIP validation and content policy

#### Prerequisites

- Proven multi-file vertical slice

#### Work

- Accept ZIP packages containing one or more candidate `.html` or `.htm` documents; no file must be named `index.html`.
- After safe extraction, present candidates and require selection of the default document before the release becomes ready.
- Reject absolute paths, traversal, symbolic links, device files, encrypted archives, archive bombs, duplicate/case-colliding paths, excessive file counts, excessive nesting, and expanded-size violations.
- Stream or bound extraction CPU, memory, disk, and elapsed time.
- Detect MIME types rather than trusting extensions.
- Add malware scanning using an approved scanner and failure policy.
- Inspect remote scripts, fetch/WebSocket targets, forms, frames, and external assets for the user-facing report.
- Enforce a default sealed CSP: local assets only, no arbitrary network requests, external scripts, frames, forms, or object/embed content.
- Add an audited approved-host exception mechanism only if pilot evidence requires it.
- Set CSP, `X-Content-Type-Options`, Referrer-Policy, Permissions-Policy, Cross-Origin-Resource-Policy, frame restrictions, safe Content-Disposition, and appropriate Cache-Control.
- Sandbox previews without `allow-same-origin` by default.
- Add quotas, rate limits, policy-exception audit events, and safe portal escaping.

Static inspection is advisory. Separate origins, cookies, storage authorization, sandboxing, and CSP are the enforcement boundaries.

#### Exit evidence

- Archive traversal, bomb, malformed archive, duplicate-path, MIME confusion, quota, and timeout tests pass.
- A ZIP with a non-`index.html` default document can be selected, previewed, published, downloaded byte-for-byte, and restored.
- Failed validation cannot place content in a release prefix.
- Default-policy applications cannot initiate arbitrary network requests.
- A hostile application cannot access another application's browser storage.
- Policy exceptions are explicit, bounded, attributable, and reversible.

- Run load, disruption, dependency-failure, telemetry-outage, backup, and restore exercises.

#### Exit evidence

- Helm install, upgrade, verification, rollback, and uninstall tests pass on a conformant disposable Kubernetes cluster through GitHub Actions.
- Docker Compose start, upgrade, verification, rollback, restart, and teardown tests pass on a clean Docker host and can be repeated locally.
- Checked, signed images and the OCI chart are published to `ghcr.io`, deployed through both profiles, verified, and rolled back using only GitHub Actions for CI/CD orchestration.
- Published content remains available during control-plane deployment and failure exercises appropriate to each profile.
- Kubernetes pod-disruption and Compose process/container restart tests pass.
- PostgreSQL restore is demonstrated with a provider-neutral procedure.
- Database records and immutable object-store releases reconcile after recovery.
- The service remains usable when telemetry delivery is unavailable.
- Eyes onboarding acceptance is complete before production signal collection is enabled.

### Milestone 7 — Pilot, cutover, and legacy retirement

#### Prerequisites

- All R1–R16 acceptance evidence available in a production-like environment

#### Work

- Use representative applications covering direct multi-file uploads, non-`index.html` default documents, ZIP assets, self-contained content, rejected external dependencies, timestamp-label collisions, localized publication display, and multi-version restore.
- Use the Campaign Advisor fixture for upload, external-dependency warning, self-contained remediation, preview, publish, download, edit, second release, restore, and roll-forward testing.
- Confirm that no application creates application-specific Kubernetes or Docker resources.
- Execute the approved migration path:
  - **Greenfield:** prove no approved production consumer or data requires migration, then retire the legacy service.
  - **Migration:** inventory apps/bundles/entrypoints/logs/URLs and object-store objects; map them to the new model; run repeatable dry runs; compare counts and digests; sample source downloads; apply a final consistency mechanism; cut over routing; reconcile; retain an approved rollback checkpoint.
- Run production deployment and rollback exclusively through GitHub Actions.
- Verify support, security, backup, restore, upgrade, and incident documentation against actual procedures.
- Remove legacy runtime access, storage permissions, DNS/routes, and runtime credentials after the rollback window closes. Legacy CI/CD integrations and publication jobs were already removed in Milestone 1.

#### Exit evidence

- Pilot users complete the primary workflow without facilitator intervention and record pass/fail results against R1–R16.
- No unresolved severity-one or severity-two defect remains.
- No unaccepted critical or high-risk security finding remains.
- Backup restoration and release reconciliation are demonstrated.
- Application restore and platform deployment rollback are both exercised.
- Migration reconciliation finds no omitted application or release, or the approved greenfield decision proves migration unnecessary.
- Only GitHub Actions can release or deploy the production platform.
- The legacy runtime and its access are retired after the approved rollback window.

## 8. Validation strategy

| Layer | Required coverage |
| --- | --- |
| Characterization | Legacy domain, API, authorization, static serving, migrations, and object-layout behavior selected for retention |
| Unit | Core entities, path/default-document validation, timestamp labels, localization inputs, authorization, state transitions, idempotency, job leases, and policy rules |
| Contract | API v2 schema and only the explicitly retained API v1 contracts |
| Integration | PostgreSQL, S3-compatible storage/MinIO, OIDC mock provider, multi-file upload completion, worker retries, quarantine cleanup, and transaction boundaries |
| Browser | Playwright multi-file/ZIP upload, default-document selection, localized publication time, preview, publish, unpublish, download, restore, authorization, and error workflows |
| Security | Multi-file path attacks, archive attacks, hostile HTML, origin/cookie isolation, CSP, token/session handling, storage credentials, upload authorization, and CI/CD permissions |
| Accessibility | Automated checks plus manual keyboard and screen-reader review of the primary workflow |
| Performance | Static reads, multi-file upload processing, worker contention, pointer updates, and resource bounds |
| Kubernetes | Helm install/upgrade/rollback/uninstall, probes, optional policies, disruption, and architecture-specific smoke tests on a conformant cluster |
| Docker | Docker Compose start/upgrade/rollback/restart/teardown and local-machine smoke tests |
| Recovery | Provider-neutral PostgreSQL restore, object-store/database reconciliation, interrupted migration, and cutover rollback |
| CI/CD | Untrusted PR isolation, trusted release, signing, `ghcr.io`/GitHub Packages publication, protected deployment, failed promotion, and rollback |

### Golden-path acceptance sequence

```text
create application
  -> upload multiple files for draft v1
  -> select app.html as the default document
  -> validate
  -> preview on untrusted origin
  -> publish as UTC timestamp version v1
  -> show Published at in the browser's local timezone
  -> download and verify v1 source files
  -> upload ZIP draft v2 with a differently named default document
  -> select default document and review policy findings
  -> publish timestamp version v2
  -> restore v1 without changing its version label
  -> roll forward to v2
  -> unpublish
```

The Campaign Advisor's browser-side behavior must remain functional after upload and download once external CDN dependencies are made self-contained or covered by an approved policy exception.

## 10. Major risks and controlling work

| Risk | Controlling work |
| --- | --- |
| Large dependency jump hides regressions | Characterization tests; vertical dependency upgrades; clean-checkout gates |
| Modernization grows into a rewrite | Preserve TypeScript and domain concepts; implement one secure vertical slice before breadth |
| Multiple delivery systems create drift | GitHub Actions-only rule; explicit CircleCI/ArgoCD prohibition; integration and credential retirement gate |
| Legacy publishing is copied without need | Consumer inventory; default retirement of website branch deploys, Docker Hub, public npm, and unused CLI artifacts; publish approved replacements only through GitHub registries |
| Unresolved security boundaries cause rework | Approve origins, cookies, identity, storage, and worker contracts before portal/API implementation |
| Arbitrary uploaded JavaScript accesses trusted state | Separate origins, host-only cookies, CSP, sandboxed previews, no privileged content-plane credentials |
| Archive processing exhausts workers | Streaming/bounded extraction, quotas, leases, retries, timeouts, resource limits, and hostile fixtures |
| Asynchronous processing creates duplicate or stuck releases | Explicit state machine, idempotent completion, leases, bounded retries, cleanup, and restart tests |
| Timestamp version labels collide or imply the wrong publish time | Opaque internal IDs, database-enforced per-application uniqueness, deterministic collision suffixes, authoritative UTC audit timestamps, and locale/timezone tests |
| Legacy data or URLs are lost at cutover | Inventory first; dry-run migration and digest/count reconciliation, or explicit greenfield evidence |
| UI work delays the usable product | Keep Ant Design; implement only the primary publishing workflow before administrative polish |
| Telemetry integration bypasses platform gates | Complete Eyes onboarding; use only provisioned product/environment access; service must tolerate telemetry outage |
| StaticDeploy becomes a general PaaS | Enforce static-only admission rules and explicit non-goals |

## 11. Definition of done

Modernization is complete only when:

- R1–R16 have retained acceptance evidence.
- The direct multi-file and ZIP workflows pass end to end with user-selected default documents that need not be named `index.html`.
- Every release is immutable and integrity-verified; ZIP originals remain exactly downloadable and direct-upload downloads preserve every source path and digest.
- First publication assigns a collision-safe UTC timestamp version label, publication audits retain authoritative UTC timestamps, and browsers display localized `Published at` values.
- Publish, unpublish, and restore are transactional pointer changes; restore does not rename the restored version.
- Portal and uploaded content use isolated origins and credentials.
- OIDC, authorization, configurable storage authentication, multi-file/archive defenses, CSP, and hostile-content tests pass.
- Multi-architecture images and the OCI Helm chart are signed and published to `ghcr.io`; any additional package is published only to GitHub Packages.
- GitHub Actions is the sole CI/CD orchestrator for checks, release, deployment, promotion, verification, and rollback.
- CircleCI and all other CI/CD systems, repository references, webhooks, publication paths, and credentials are removed or disabled.
- Both Helm and Docker Compose deployment profiles pass install/start, upgrade, verification, rollback, and recovery tests without a required cloud provider.
- PostgreSQL restore and S3-compatible object-store/database reconciliation are proven.
- Published content remains available during control-plane maintenance.
- Required runbooks, dashboards, and alerts are validated, and Eyes onboarding gates are satisfied before production collection.
- Migration is reconciled or an approved greenfield decision proves it unnecessary.
- No application upload creates per-application Kubernetes or Docker resources.
- The legacy platform is retired after the approved rollback window.

The governing scope decision remains: **StaticDeploy is an artifact registry and serving platform for static browser applications, not a general application platform.**
